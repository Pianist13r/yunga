# Протокол изменения (`consent.md`) — единый порядок для любой правки настроек ученика

Источник — DESIGN-v1.md §8.1. Этому порядку следует Claude **каждый раз**, когда шаг курса меняет что-то за пределами журнала/проекта ученика: `~/.claude/settings.json`, `~/.claude/CLAUDE.md`, `.mcp.json`, файлы `.env` и подобное. Внутри журнала (`yunga-zhurnal/`) и проекта ученика (`yunga-proekt/`) протокол не нужен — там разрешение уже дано доступом к папке (M02).

## Пять шагов, строго по порядку

1. **Показ.** Словами, без жаргона: что было → что станет, и отдельно — «что это изменит для тебя» (не только техническое описание). Диff — по желанию ученика, не обязателен. Плюс: зачем это нужно, где будет лежать бэкап, как откатить, если не понравится.
2. **Явное «да».** Ждём одно ясное согласие на одно конкретное действие. **Молчание, «угу», «ну давай», «наверное» — это не «да»** — переспросить прямо: «делать?». Одно «да» = одно действие; для следующей правки — заново с шага 1.
3. **Бэкап.** Копия трогаемого файла (или файлов) командой ОС (`copy`/`Copy-Item`, не Read — чтобы не выводить содержимое, в котором могут быть секреты) в `yunga-zhurnal/backups/<дата>_<что>/` + запись в `manifest.md` этой папки (имя файла, путь-источник, размер, sha256 — формат описи задан в `backup-rollback.md`). Файлы с потенциальными секретами (`settings.json`, `.env`) — только копированием, без чтения содержимого при снятии копии.
4. **Правка — Edit/Write, никогда shell.** `/rewind` не откатывает изменения, сделанные через `Bash`/`PowerShell` (checkpointing.md:70-72) — значит откат по этому протоколу перестаёт работать, если правка прошла мимо Edit/Write. Инструмент `Edit` — для точечной замены строки/блока, `Write` — только когда файла ещё нет.
5. **Проверка и запись.**
   - Для `settings.json` — команда `/doctor` только смотрит: она сама предлагает правки и спрашивает подтверждение ДО изменения — на любые её предложения отвечаем «нет» в моменте, а то, что действительно нужно, делаем отдельным шагом по этому же протоколу (не через `/doctor`).
   - Для скилла — проверка, что он срабатывает (вызов по команде или по описанию).
   - Для хука — проверка триггером (действие, которое должно его вызвать).
   - Для правила разрешений — вызов действия, которое правило должно поймать, и ответ «No» на диалог (не даём действию реально пройти, если это не была цель проверки).
   - Итог записывается строкой в `changes.md` журнала: `CH-NNN | дата+пояс | файл | что изменено | зачем | путь к бэкапу | как откатить | как проверено`.

## Что курс никогда не делает через этот протокол

- **Не удаляет** — «убрать» всегда означает переместить в `Архив/` журнала, не стереть.
- **Не меняет режим разрешений** ученика без отдельного, ещё более явного разговора (M02) — это не рядовая правка настроек.
- **Не предлагает `bypass`** ни на каком шаге курса.

## Откат (`otkat`)

Без аргумента — список последних изменений из `changes.md` словами: «было → станет → что изменится для тебя», diff — по желанию → «да» → восстановление файла(ов) из соответствующего бэкапа → новая строка в `changes.md` с пометкой «откат CH-NNN». Тот же протокол, только в обратную сторону — показ и «да» нужны и здесь.

## Проверка целостности после серии правок

В конце этапа (или любой момент по просьбе ученика) — сверка живого файла с последним снятым бэкапом (`diff`/сравнение по sha256), а не «на глаз»: значения могли разъехаться по причинам, не связанным с курсом (другая сессия, сам Claude Code). Расхождение сверх того, что записано в `changes.md`, — повод остановиться и разобраться, а не продолжать молча.
